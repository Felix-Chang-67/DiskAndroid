# 测试节点 N3c：蓝光 AACS 逐盘精确诊断 + 总线加密不再一刀切

- 版本：`0.10.2-N3c`（versionCode 14），直接覆盖安装。
- **蓝光解密组件 libaacs.so 改过了，要重新导入**（DVD 的 libdvdcss.so 和 KEYDB.cfg 不用动）。

## 这次按你提的六点，逐盘查了 N3 的日志，结论先说清楚

你的两张 HITORIE 蓝光，卡点**不一样**，都不是"缺官方证书"一句话能概括的：

| | 盘 1（盘 ID 9f3483f6…） | 盘 2（盘 ID 1e0e1791…） |
|---|---|---|
| 读盘 / UDF / AACS 文件 | ✅ 全部正常读出 | ✅ 全部正常读出 |
| MKB 版本 | 61 | 76 |
| 媒体密钥 MK | ✅ 用 KEYDB 的处理密钥**算出来了** | ❌ **算不出**（KEYDB 的密钥覆盖不到 v76） |
| 这张盘的 VUK / 卷标识 | ❌ 不在 KEYDB（你的库 **0 个光盘条目**） | ❌ 不在 KEYDB |
| 真正卡在哪 | 差最后一步 VID（要向光驱认证，光驱拒证书） | 更早一步就停了（连 MK 都没有） |

**共同点：你导入的 KEYDB.cfg 里一个"逐盘 VUK 条目"都没有。** 它是"设备密钥 + 处理密钥"型的库；要直接解盘，需要的是"逐盘 VUK"型的库（里面按盘 ID 列出每张盘的 VUK）。

## 这次改了什么（都是真能在 Android 上跑的，不是空谈）

1. **逐盘精确分类**（你的第 2、3、5、6 点）：打开蓝光失败时，日志和"视频内容"里按真实原因分类，不再笼统说"缺证书"：
   - `算不出媒体密钥`：KEYDB 的处理/设备密钥覆盖不到这张盘的 MKB 版本（盘 2 就是这种）。
   - `缺这张盘的 VUK，要向光驱认证`：MK 算出来了，只差卷标识，要认证读取（盘 1 就是这种）。
   - `视频真被总线加密`：见下。
   - 每张盘都会打一行 `DiskAndroid AACS summary: mkbv=… bee=… bec=… unit_keys=… result=…`，一眼看出走到哪一步。
2. **BEE=1 不再一刀切**（你的第 4 点）：以前只要内容证书的"总线加密"标志是 1，就直接拒绝。实际上这个标志**不等于视频真的被总线加密**。现在只要能拿到这张盘的 VUK，就**先按"只解单元层"试**，让真实数据的 TS 校验来判定：
   - 如果视频其实没被总线加密 → 直接就能播。
   - 如果视频真被总线加密 → 播放时提示"视频确实被总线加密，只有 VUK 不够"。
   - 这一步只在"有 VUK"时才有意义。
3. **复核读取链路**（你的第 1 点）：确认 USB 读盘、UDF、`index.bdmv`/`AACS/MKB_RO.inf`/`Content*.cer`/`Unit_Key_RO.inf` 读取全部正常——这块本来就没问题，不是瓶颈。

## 老实说：这两张盘这次大概率还是播不了，原因很具体

- 盘 2：KEYDB 连 MK 都算不出来。除非换一个**含这张盘 VUK 的 KEYDB**，否则无解——这跟证书无关。
- 盘 1：差一个这张盘的 VUK / 卷标识。有了它就跳过认证。
- 两张盘都开了总线加密标志。**即使补上 VUK**，如果视频确实被总线加密，在这台支持总线加密的光驱上仍要认证；但这次改完，App 会**实际去试、并告诉你到底是哪种**，而不是一看标志就放弃。

**唯一能让这两张盘在本机前进的具体条件：一个含这两张盘 VUK 条目的 KEYDB.cfg。** 这属于密钥库内容，由你自己准备/导入（和一开始的约定一致，我不提供任何密钥）。你现在这个 66 MB 的库是"处理密钥"型、0 个光盘条目；"逐盘 VUK"型的库是另一种。导入那种之后：
- 盘 2 如果库里有它的 VUK → 能算出单元密钥。
- 盘 1 同理。
- 然后 App 会按上面第 2 点，先试只解单元层；真被总线加密才会卡住。
