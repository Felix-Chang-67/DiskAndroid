# DiskAndroid 蓝光（AACS）解密技术报告

- 适用版本：0.10.2-N3c（versionCode 14）
- 范围：Android 平板 + USB 外接蓝光光驱，免 root，用户态发 SCSI/MMC，原生播放器边读边播。
- 定位：**仅限个人播放**。解密做成可选外部组件，不内置进 App；不提供解密后导出；"读成 ISO"对加密盘保持原始密文；地区码只读不改；写盘命令在最底层永久拦截。

---

## 1. 结论速览

- 蓝光的 AACS 解密由一个**外部组件 `libaacs.so`**（libaacs 0.12.0 + libgcrypt + libgpg-error，打了 DiskAndroid 补丁）完成，组件不随 App 分发、不进仓库，由用户导入。
- 组件在 Android 上没有内核光驱驱动，所有 MMC 认证命令经一个**宿主回调接口**交给 App，由光驱会话发出，照样过只读守卫和命令日志。
- 解密密钥来自用户自备的 **KEYDB.cfg**。App 不提供任何密钥。
- 能播的边界：**非总线加密、且 KEYDB 里有这张盘 VUK 条目**的蓝光。
- 不能播的硬墙：**总线加密**（需要向光驱做 AACS 认证，而认证需要一份未被吊销的主机证书，公开 KEYDB 里那份已被吊销）；以及 **KEYDB 覆盖不到的新盘**（连媒体密钥都算不出）。
- 不支持：AACS 2.0（4K UHD）、BD+。

## 2. 总体架构

```
 ┌─────────────────────────── App（Kotlin / Compose）────────────────────────────┐
 │ VideoPlaybackController   DecryptComponents（导入/校验/KEYDB 查找）             │
 │ VideoSection（逐盘预判）   DriveSectorReader.scsi（认证命令入口，标 sensitive） │
 └───────────────┬───────────────────────────────────────────────┬──────────────┘
                 │ JNI（NativeBridge）                             │ scsi() 回调
                 ▼                                                 ▼
 ┌──────────── native/diskplayer（C）────────────┐   ┌──────── core:scsi / core:drive ────────┐
 │ dp_bd  ── libbluray 1.5.0（导航/解复用）       │   │ ReadOnlyGuard（只读白名单 + 认证格式）  │
 │   │      bd_open_stream（读盘回调→dp_source）  │   │ DriveSession（单线程命令队列）          │
 │   │      bd_get_disc_info（AACS/BD+ 状态）     │   │ BOT（USB Bulk-Only Transport）          │
 │   ▼                                            │   └────────────────┬───────────────────────┘
 │ dc_host.h（宿主接口 ABI）                      │                    │ READ(10) / REPORT KEY …
 │   ▲ aacs_set_host()                            │                    ▼
 │ libaacs.so（外部组件，dlopen）────────────────┼──→ 认证命令经 host_scsi → SectorReader.scsi
 └────────────────────────────────────────────────┘
```

- **libbluray** 负责 BDMV 导航（First Play、菜单、标题/播放列表、HDMV 虚拟机）和 M2TS 解复用；解密由它 dlopen 的 libaacs 完成（环境变量 `LIBAACS_PATH`）。
- **libaacs** 需要发 MMC 认证命令。原本它在 Linux 上走 `/dev/sr0` 的 ioctl；本项目把它的 MMC 后端换成"经宿主回调发命令"。
- 两条读盘路径：① 视频数据经 `bd_open_stream` 的读回调 → `dp_source`（预读缓存）→ JNI → 光驱会话 READ(10)；② 认证命令经 `dc_host.h` 的 `scsi()` 回调 → `SectorReader.scsi` → 光驱会话。两条都经只读守卫与日志。

## 3. 解密组件 libaacs.so

| 项 | 内容 |
|---|---|
| 上游 | libaacs 0.12.0（VideoLAN）+ libgcrypt 1.12.4 + libgpg-error 1.61（GnuPG） |
| 来源固定 | 三者都按 SHA-256 固定；libgcrypt / libgpg-error 的 SHA-256 是核对过 GnuPG 发布签名之后记下的 |
| 链接方式 | libgcrypt、libgpg-error **静态**链进同一个 `libaacs.so`；只导出 `aacs_*`（版本脚本），静态库符号不导出 |
| 裁剪 | libgcrypt 只编 AES、SHA-1/2/3、BLAKE2（KDF 模块需要）、ECC；arm64 用 ARMv8 加密指令 |
| 产物 | arm64-v8a，16 KB 页对齐（`-Wl,-z,max-page-size=16384`），约 0.87 MB |
| 分发 | **不进 APK、不进仓库**；由用户在"解密组件"卡片里导入，保存为 `files/plugins/aacs/libaacs-<哈希>.so.0`，设为只读 |
| 编译脚本 | `plugins/decrypt/build_aacs.sh`（由 `build.sh android-arm64 aacs` 引入） |

构建要点：libgpg-error 交叉编译需要 aarch64 的锁对象头文件，源码包里是 `…-androideabi.h`（40 字节，和 bionic 在 aarch64 上的 `pthread_mutex_t` 同大小），复制成 configure 得出的 `…-android.h` 名字即可。

文件名以 `.so.0` 结尾：libbluray 按 `LIBAACS_PATH` + `.so.0` 加载。

## 4. 宿主接口 dc_host.h 与只读守卫

### 4.1 接口（App 与组件各一份，改动时同步升版本号）

```c
#define DC_HOST_API_VERSION 1
enum { DC_DIR_NONE=0, DC_DIR_IN=1, DC_DIR_OUT=2 };   /* 无数据 / 光驱→主机 / 主机→光驱 */
typedef struct dc_host_api {
    int version; void *opaque;
    int (*scsi)(void *opaque, const uint8_t *cdb, int cdb_len, int dir,
                uint8_t *buf, int buf_len, uint8_t *sense, int *sense_len, int timeout_ms);
    void (*log)(void *opaque, int level, const char *msg);
} dc_host_api;
```

- 返回：0 = GOOD；>0 = CHECK CONDITION（sense 写回，长度回填）；<0 = 没发成（断开/传输错/被守卫拒）。
- 组件导出 `aacs_set_host()` 接收它；App 在 `nativeAttachAacs` 里调用，并 `setenv LIBAACS_PATH / XDG_CONFIG_HOME / XDG_CACHE_HOME`。

### 4.2 只读守卫（`ReadOnlyGuard.kt`）放行的 AACS 格式

认证命令和普通读盘命令一样过守卫；只放行认证真正用到的格式，其余一律拒绝，**设置地区码 SEND KEY 06h 永久拦截**：

| 命令 | KEY CLASS | 放行的 KEY FORMAT |
|---|---|---|
| REPORT KEY（A4h，读） | 02h（AACS） | 00h AGID、01h 光驱证书+Challenge、02h 光驱密钥、38h 光驱证书、3Fh 作废 AGID |
| SEND KEY（A3h，Data-Out） | 02h（AACS） | 01h 主机证书+Challenge、02h 主机密钥、3Fh 作废 AGID |
| READ DISC STRUCTURE（ADh，读） | 媒体类型 1（BD） | 格式 80h 卷标识、81h 序列号、83h MKB、84h 数据密钥 |

命令日志里，认证命令标 `sensitive`：CDB、结果、原始 sense 照记，**密钥类载荷不写进日志**。

## 6. AACS 密钥获取流程（libaacs 的"瀑布"）

打开一张盘时，libaacs 依次尝试（任一步成功即解密可用）：

1. **读盘上文件**：`AACS/Unit_Key_RO.inf`（算盘 ID = 它的 SHA-1）、`AACS/MKB_RO.inf`（MKB 版本）、`AACS/Content000.cer`（内容证书，含总线加密标志）、`AACS/CPSUnitNNNNN.cci`（CPS 单元使用规则）。
2. **查 KEYDB / 缓存求 VUK**：
   - KEYDB 里这张盘的 **VUK** 条目 → 直接得卷唯一密钥（最省事，不碰光驱）。
   - 缓存里的 VUK / MK。
   - 用 KEYDB 的**处理密钥 / 设备密钥**算出**媒体密钥 MK**（能不能算出取决于 KEYDB 覆不覆盖这张盘的 MKB 版本）。
3. **求卷标识 VID**（当只有 MK、没有 VUK 时）：KEYDB 里的 VID → 或向光驱**认证读取**（REPORT KEY/SEND KEY 一整套，需要未吊销的主机证书）。
4. **VUK = AES-128D(MK, VID) ⊕ VID** → 再算每个 CPS 单元的**单元密钥**。
5. **总线加密读数据密钥 RDK**（当内容证书 BEE=1 且光驱支持总线加密时）：向光驱认证读取（见 §7），按光驱证书哈希缓存一份（`rdk/<drive_cert_hash>`，同一光驱各盘共用）。
6. **解密**：每个 6144 字节对齐单元，先（若有）解总线层，再用单元密钥解 AACS 单元层；用 TS 同步字（每 192 字节一个 0x47）校验结果是否正确。

关键点：**VUK 要么来自 KEYDB，要么来自认证后读到的 VID**。没有 KEYDB 条目、又认证不了，就卡在第 3 步。

---

## 7. 总线加密（Bus Encryption）处理

- **BEE 标志**：盘上内容证书第 2 字节最高位（libaacs 与本项目 `bus_encryption_flag()` 各读一次、互相印证）。它表示"这张盘的内容**可能**被总线加密"。
- **实际是否加密**：只有当 BEE=1 **且光驱也支持总线加密**时，光驱才会把 USB 上发出的数据再裹一层，解这层要 RDK；而 RDK 只能通过 AACS 认证拿到。
- **N3c 改进（`aacs_open_device`）**：BEE=1 不等于视频真被总线加密。原版 libaacs 一旦 BEE 成立、拿不到 RDK 就整盘失败；补丁改为——**已有单元密钥但拿不到 RDK 时，置 `bec=0` 继续**，让播放时每个单元的 TS 校验来判定：
  - 视频其实没被总线加密 → 单元层解出合法 TS → 正常播放。
  - 视频真被总线加密 → 单元层解出乱码 → libbluray 报 `BD_EVENT_ENCRYPTED` → App 提示"视频确实被总线加密，只有 VUK 不够"。
  - 这一步只在"有 VUK/单元密钥"时才有意义。

## 8. 失败分类（libaacs 错误码 → App 提示）

`dp_bd.c` 的 `aacs_error_text()` 按真实错误码分类，不笼统归为"缺证书"：

| 错误码 | 含义 | App 提示（要点） |
|---|---|---|
| 0 | 成功 | 正常播放 |
| -1 | AACS 文件读不出 | AACS 目录损坏或读盘出错 |
| -2 | 没有 KEYDB.cfg | 请导入密钥库 |
| -3 | 无处理密钥 | KEYDB 覆盖不到这张盘的 MKB 版本，且无 VUK 条目 → **需含该盘 VUK 的 KEYDB** |
| -4 | 无主机证书 | 缺 VUK，又无证书可认证 |
| -5 / -7 | 证书被吊销 / 认证出错 | MK 算出了，差 VUK/VID，向光驱认证被拒 → **补该盘 VUK 即可跳过认证** |
| -6 | 光驱无 AACS 功能 | 光驱不报告 AACS |
| -8 | 无设备密钥 | 同 -3（设备密钥覆盖不到） |
| -10 | AACS 2.0 | 不支持 4K UHD |

每盘另打一行：`DiskAndroid AACS summary: mkbv=… bee=… bec=… unit_keys=… result=…`。

## 9. KEYDB.cfg（两种库，决定能走哪条路）

- **处理密钥 / 设备密钥型**：含 `| DK |`、`| PK |`、`| HC |`，靠算法算 MK，再认证读 VID。只对 KEYDB 覆盖得到的 MKB 版本有效；对总线加密盘，认证这一步还要未吊销的证书。
- **逐盘 VUK 型**：按盘 ID 列出每张盘的 `| V |`（VUK）等，直接给密钥，不用算 MK、不用读 VID。这是绕开"认证读 VID"唯一的软件途径。

App 侧 `DecryptComponents.keydbHas(discId)` 会按盘 ID 在 KEYDB 里查这张盘，并在日志/预判里说明"有/没有这张盘的 VUK 条目"。密钥库由用户自备导入，App 不提供任何密钥。

---

## 10. AACS 2.0 / BD+

- **AACS 2.0（4K UHD）**：`index.bdmv` 版本 0300 即判定为 UHD，直接拒绝（即使 KEYDB 有密钥也不试）。
- **BD+**：libbluray 的 `bdplus_detected`；没有 libbdplus，直接提示不支持（硬播会大片花屏）。

| | 盘 1 | 盘 2 |
|---|---|---|
| 盘 ID | 9f3483f6… | 1e0e1791… |
| MKB 版本 | 61 | 76 |
| BEE | 1（开） | 1（开） |

## 13. 能播 / 不能播的边界与密码学硬墙

**能播**：
- 没加密的蓝光（自制 BDMV / AVCHD）。
- AACS 盘，且 **KEYDB 里有这张盘的 VUK 条目**，且视频没有真被总线加密（N3c 后由 TS 校验实测判定）。

**不能播（且软件无法绕过）**：
- **总线加密真被应用**：解总线层要 RDK，RDK 只能靠 AACS 认证取得，认证要一份未被吊销的主机证书。公开 KEYDB 里那份已被吊销，新盘的吊销名单里就有它，光驱直接拒（5/6f/00）。这是 AACS 的设计目的，不是实现 bug。
- **KEYDB 覆盖不到的新盘**：连 MK 都算不出（盘 2）。只有"逐盘 VUK 型"KEYDB 里有这张盘才行。

**为什么不能凭空解决**：VUK 需要卷标识 VID，VID 只能从 KEYDB 取或向光驱认证取；认证要未吊销证书。有效证书只授权给持牌播放器，无法计算、本项目也不提取或内置任何泄露密钥。因此软件侧唯一能前进的方向，是导入一个含这些盘 VUK 的 KEYDB.cfg（内容由用户自备）。
